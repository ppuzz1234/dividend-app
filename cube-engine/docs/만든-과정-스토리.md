# 만든 과정 (Development Journey) — CUBE (A4) 발표용 스토리

> **왜 이 문서?** 결과물(작동하는 엔진)보다 **만든 과정**이 더 중요하다는 기준에 따라, "그날그날 어떤 문제를 만나 어떻게 결정했는가"를 **스토리**로 남긴다. 특히 CUBE는 세법을 다루므로 **"왜 이 값을 믿을 수 있는가"의 근거 사슬 자체가 제품**이다 — 과정이 곧 결과다.
> 각 항목 = **계기 → 문제/진단 → 결정(왜) → 검증 → 배운 것**. (기술 상세는 [진행기록.md](진행기록.md)·[변경사항-*.md](.), 순서별 설계는 [ORDER2-REJECTION-MATRIX.md](ORDER2-REJECTION-MATRIX.md)·[ORDER3-ORDERING-MATRIX.md](ORDER3-ORDERING-MATRIX.md).)
>
> **한 줄 관통 주제:** *"조용히 틀리느니 시끄럽게 멈춘다."*
> — 이 프로젝트에서 가장 위험한 실패는 크래시가 아니라 **그럴듯하게 틀린 세법 값**이다. 그래서 코드 전반에 "조용히 넘어가지 마"라는 장치를 박고, 모르는 건 아는 척하지 않고 모른다고 표시한다.

## 0. 전체 그림 (한 장)

CUBE는 절세 3종 계좌(ISA·연금저축·IRP)의 **팩트 엔진(미션 1)** 과 **플래닝 룰엔진(미션 2)** 이다.
둘은 각자 세법을 알지 않는다. **동일한 Authoritative Policy Registry 하나**를 공유하고(사양 §1.1, split-brain 금지), 모든 값은 원문 조문에 묶인다.

```
[법령 원문]  →  [Source Snapshot]  →  (사람 승인)  →  [Policy Pack]  →  ┬→ 미션 1 FACT 엔진
  법제처 API      packages/corpus      Maker-Checker    packages/policy   └→ 미션 2 PLAN 룰엔진
                  ← 이번 세션이 여기
```

사양 §13의 구현 순서: **0~3 완료**(numeric / policy schema+loader / engine ordering) → **4 = 정책 코퍼스 원문 수집(이번 세션)** → 5 Tax Calculator → 6 Optimizer → 7 AI 층 → 8 데모.

**이 세션이 채운 것:** 위 그림의 첫 화살표. 그전까지 `packages/policy`는 정책 팩의 `source_id`를 검사했지만 **그 id가 가리키는 실물이 레포에 없었다.** 검사는 있는데 검사 대상이 없는 상태였다.

## 1. 7.31 — "RAG를 만들자"에서 "만들 수 없다"를 발견하기까지

**계기.** 사용자가 *"Mission 1(RAG)을 develop하고 싶다"* 로 세션을 열었다. 자연스러운 다음 단계로 보였다 — 순서 0~3이 끝났고, 남은 미션 1은 RAG니까.

**문제/진단.** 착수 전에 `packages/policy`를 읽다가 막혔다. 정책 팩은 `sources[].source_id`로 근거 조문을 참조하고, `loadPolicyPack.ts`는 그 참조를 검사한다. 그런데 그 검사가 하는 일은 **"같은 팩 안에서 그 id가 선언돼 있는가"** 뿐이었다. 팩 안에서 닫혀 있고, 바깥의 실물(원문 조문)과는 연결이 없었다.

→ **재인식:** 이건 "RAG가 아직 없다"가 아니라 **"두 미션을 잇는 이음매가 비어 있다"** 였다. 사양 §1.1은 두 미션이 동일한 Registry를 공유해야 한다(split-brain 금지)고 못 박았는데, 그 Registry가 참조하는 출처의 **실체**가 없었다. 그리고 사양 §5.1의 핵심 불변식 **"PRIMARY source 없이 effect 기재 불가"**(순서 2에서 R05·R06으로 코드화된 것)를 지킬 **물리적 근거**가 부재했다.

RAG는 색인할 원문이 있어야 색인을 한다. 사양 §13의 **순서 4 "정책 코퍼스 원문 수집"이 미착수**인 채로 순서 5 이후를 건드리려던 것이었다.

**결정(왜).** **이번 세션 목표를 RAG에서 순서 4로 교체.** 사양 §13의 순서는 관료적 절차가 아니라 **의존성 그래프**다. 순서를 건너뛰고 RAG를 만들었으면 색인할 게 없었거나, 더 나쁘게는 내가 아는 세법 지식으로 빈 값을 채웠을 것이다(CLAUDE.md "하지 말 것" 2번이 정확히 금지하는 것).

**검증.** `packages/policy`의 로더가 실제로 팩 내부 참조만 검사한다는 것, 그리고 레포 어디에도 원문 저장소가 없다는 것을 코드에서 직접 확인.
부수적으로 — 사용자가 *"내 OpenAPI로 하면 되나?"* 라고 물었을 때 MyWork 전체 `.env` 변수명을 훑어봤고, **법령 API 키는 어디에도 없었다.** A4/.env에 있던 4개는 다른 Vite 프로젝트 잔재(Supabase·Google·YouTube)였다. → 새로 발급 필요.

**배운 것.** *"다음에 뭘 만들까"보다 "지금 만들려는 것이 무엇에 의존하는가"를 먼저 본다.* 순서를 건너뛰면 만들 수는 있지만, 만든 게 무엇에 근거하는지 아무도 답할 수 없게 된다. 그리고 **"키가 있나?"는 추측이 아니라 실제 파일을 grep해서 답한다** — 없으면 없다고 말하고 발급받으면 된다.

## 2. 7.31 — 수집 단위 결정: "지금 필요한 조문"이 아니라 "그 법 전체"

**계기.** 국가법령정보 OPEN API에는 `JO` 파라미터가 있다. 조문번호를 주면 그 조문만 받을 수 있다. §12가 요구하는 조문은 7개니까, 7번 호출하면 끝나 보였다.

**문제/진단.** 처음엔 그게 lazy해 보였다 — 필요한 것만 받으면 되니까. 그런데 **사양 §1.2를 다시 읽자 그림이 뒤집혔다.**

사양은 FACT 답변을 **2클래스**로 나눈다:
- `REGISTRY_RESOLVED_FACT` — Registry 룰로 승격된 조문에 근거한 확정 팩트
- `UNMODELED_OFFICIAL_SOURCE` — 아직 모델링하지 않았지만 **원문은 인용할 수 있는** 것

→ 두 번째 클래스가 존재하는 이유는 **"모른다"와 "원문은 있으나 미모델링"을 구분하기 위해서다.** §12 밖 질문이 들어왔을 때 "모릅니다"로 끝내는 것과 "이 조문 원문은 이렇습니다, 다만 저희 엔진이 계산에 쓰는 값으로는 아직 승격하지 않았습니다"는 완전히 다른 답이다. **그리고 후자는 전 조문을 갖고 있어야만 가능하다.**

**결정(왜).** **JO를 주지 않고 MST 하나로 전 조문 일괄 수신.** 두 가지 이유:
1. 호출 1번으로 그 법 전체가 확보돼, 나중에 §12 밖 조문이 필요해져도 **재수집이 없다.**
2. **사양 §1.2의 FACT 2클래스가 데이터 전략에 그대로 매핑된다.** §12 목록 조문 → Registry 룰로 승격 → `REGISTRY_RESOLVED_FACT`. 나머지 1,842개 조문 → `UNMODELED_OFFICIAL_SOURCE`로 원문 인용만.

버린 대안: "필요한 7개만" — 당장은 작지만 §12 밖 질문에 답할 능력이 구조적으로 사라진다. 그리고 조문 하나 더 필요할 때마다 API를 다시 부르게 된다.

**검증.** 6개 법령 **1,849 조문**을 6번 호출로 확보. §12가 이름 대고 요구한 7개 조문(`TAXEX_91_18`·`INCTAX_59_3`·`INCTAX_61`·`INCTAX_129`·`INCTAX_D_40_2`·`INCTAX_D_40_3`·`INCTAX_D_118_3`)이 전부 스냅샷 안에 있음을 확인.

**배운 것.** *lazy의 기준은 "지금 코드가 짧은가"가 아니라 "나중에 다시 안 해도 되는가"다.* 그리고 **사양의 타입 설계(FACT 2클래스)가 데이터 수집 전략을 결정했다** — 사양을 "지켜야 할 규칙"이 아니라 "이미 답을 담고 있는 설계"로 읽으면 결정이 빨라진다.

## 3. 7.31 — ★ 버그 3개: 전부 "에러를 내지 않는" 종류였다

이 세션의 핵심이다. 셋 다 크래시하지 않고, 셋 다 그럴듯한 데이터를 만들었다. 잡힌 이유는 **미리 박아둔 방어 장치** 하나씩 때문이다.

### 3.1 버그 1 — 전문/조문 혼입으로 `source_id` 충돌

**계기.** 첫 수집 실행. **6건 중 5건 실패.**

**문제/진단.** 처음 짠 휴리스틱은 "조문번호가 비면 편·장·절 표제니까 건너뛴다"였다. 안 먹혔다.
→ 응답을 직접 뜯어보니 `조문여부` 필드가 `"조문"`(조특법 기준 458개) / `"전문"`(35개)으로 갈렸다. `"전문"`은 "제1장 총칙" 같은 편·장·절 표제인데 — **자기 번호가 없어서 뒤따르는 조문의 번호를 그대로 달고 온다.** "제1장 총칙"의 조문번호가 `"1"`이다. 즉 **번호가 비어 있는 게 아니라 남의 번호를 달고 있었다.** 내 휴리스틱이 겨냥한 조건이 아예 성립하지 않았던 것.

**결정(왜).** 추정을 버리고 **명시 필드**로 — `if (str(rec, "조문여부") !== "조문") continue;`
"번호가 비었는지"는 내가 관찰한 부수 현상이고, `조문여부`는 API가 **직접 말해주는 사실**이다. 관찰한 패턴보다 선언된 필드를 믿는다.
부칙도 확인했다 — `법령.조문`이 아니라 `법령.부칙`에 따로 있어 애초에 안 섞인다.

**검증.** 수정 후 6/6 성공. 테스트 7번("편·장·절 표제는 뒤 조문의 번호를 달고 오므로 반드시 걸러낸다")으로 고정.

**★ 배운 것 — 이 항목이 이 세션에서 가장 중요하다.**
첫판에 유일하게 "성공"한 `RETIRE_D`(79 조문)도 **충돌만 안 났을 뿐 같은 오염 위험**에 놓여 있었다. 우연히 표제와 조문 번호가 겹치지 않았을 뿐이다.
**만약 충돌 시 "그냥 덮어쓰기"로 짰다면 6개 전부 조용히 성공했을 것이고, 오염된 코퍼스 위에 정책 팩을 쌓았을 것이다.**
→ *"실패 5건"이라는 나쁜 결과가 사실은 방어 장치가 일한 증거였다.* 거절 조건을 짜는 건 비용이 아니라 보험이다.

### 3.2 버그 2 — 조문 첫 문장이 맨 뒤로 밀림

**계기.** 조립된 원문을 눈으로 읽는데 "제91조의18(개인종합자산관리계좌에 대한 과세특례)"라는 헤더가 **항·호 다음에** 나왔다.

**문제/진단.** 응답 최상위 key 순서가 `조문번호 | … | 조문키 | 항 | 조문내용 | 조문제목 | …` 이었다. key 순서대로 훑는 방식이 그 순서를 그대로 물려받았다. **모든 조문에서** 발생했다.

**결정(왜).** key 순서 의존을 통째로 폐기하고 **명시적 조립**(조문내용 → 항 → 호 → 목). JSON object의 key 순서는 스펙상 의미가 없고, 서버가 필드를 추가하면 언제든 바뀐다. "지금 순서가 맞으니 그대로 쓴다"는 **다음 API 업데이트에 조용히 깨질 코드**다.

**검증.** 테스트 1번("응답 key 순서와 무관하게 조문 첫 문장이 맨 앞에 온다")으로 고정.

**배운 것.** *외부 JSON의 key 순서에 절대 기대지 않는다.* 이건 "이번엔 운이 나빴다"가 아니라 원래 기대면 안 되는 것이었다.

### 3.3 버그 3 — 세목 유실 (가장 위험했음)

**계기.** 증상이 **없었다.** 저장은 정상, 원문도 그럴듯했다. 자체 검산 장치가 throw해서 알았다.

**문제/진단 (2단계였다).**
- **1단계 — 검산이 먼저 잡은 건 내 비교 로직의 버그였다.** ① 줄 수와 조각 수를 혼동했다(원문 문자열 안에 줄바꿈이 들어 있는 조문이 실제로 있다). ② 빈 목에 `[각 목]` 표식만 붙어 **유령 조각**이 생겼다. 둘 다 고쳤다.
- **2단계 — 그러고 나서야 진짜 원인이 드러났다.** `목내용`이 문자열이 아니라 **배열의 배열**로 오는 경우가 있다. 목 아래 `(1)(2)(3)` 세목이 중첩 배열에 들어 있다. 실례는 **소득세법 시행령 §20 ① 나목**(일용근로자에서 제외되는 업무 목록).
  **그리고 조립 함수와 검산 함수 둘 다 이걸 버리고 있었다** — 즉 검산도 같은 눈으로 세고 있어서 개수가 맞아떨어졌다. 두 함수의 시야가 같으면 검산이 검산이 아니다.

**결정(왜).** `textsOf()` 하나로 **재귀 평탄화**(문자열·숫자·중첩 배열 전부 처리)하고, **조립과 검산이 같은 함수를 쓰게** 통일. 앞으로 어느 계층이 배열로 오든 둘 다 같이 본다.

**검증.** **되찾은 원문 6만 5천여 자** — 1,852,000자 → **1,917,666자.** 테스트 4번("목내용이 중첩 배열로 와도 세목까지 전부 살린다")으로 고정.

**배운 것.** *증상이 없는 버그는 검산 장치가 없으면 영원히 안 보인다.* 이 프로젝트에서 **잘린 원문은 요약본과 구분되지 않고**, 요약된 원문 위에 세법 값을 세우면 근거 사슬이 조용히 끊어진다. 그래서 `parse.ts`의 검산은 "혹시 몰라서"가 아니라 **필수 부품**이다.
그리고 곁가지 교훈 — *검산 장치가 처음 잡는 건 대개 검산 장치 자신의 버그다.* 거기서 "검산이 시끄러우니 끄자"로 가면 진짜 버그를 영원히 못 만난다.

## 4. 7.31 — ★ 측정 후 기각한 heuristic: 80.3%는 "꽤 맞음"이 아니라 "5건 중 1건 틀림"

**발표에서 제일 좋은 대목이다.**

**계기.** 조문을 조립하다 이상한 걸 봤다. API가 `목`을 `호`의 자식이 아니라 **`항`의 형제**로 내려준다. 한 항의 여러 호에 걸린 목이 하나의 **평평한 배열**로 합쳐지고 **부모 호 참조가 없다.** 실측 — 조특법 §91의18 ③ = **호 5개에 목 9개**, 목번호가 `가·나·다` 다음 또 `가·나·다·라·마·바`로 리셋된다.

**문제/진단 — 이게 왜 심각한가.** 그냥 순서대로 이어붙이면 **목이 마지막 호에 속한 것처럼 읽힌다.** 실제 사고 사례가 하필 ISA 비과세 한도(§91의18 ②)였다:

```
1. 다음 각 목의 어느 하나에 해당하는 경우: 400만원   ← 가·나·다는 여기 소속
2. 제1호에 해당하지 아니하는 자의 경우: 200만원
가. 직전 과세기간의 총급여액이 5천만원 이하인 거주자…   ← 2번 뒤에 붙음
```

읽으면 **"총급여 5천만원 이하 → 200만원"으로 뒤집힌다.** 실제로는 400만원(서민형)이다.
→ **사양 §12에서 1순위로 지정된 파라미터가 정반대가 되는 상황.** 그리고 이건 크래시가 아니라 "그럴듯하게 틀린 답"이다.

**heuristic 후보가 있었다.** 법률 작성 관행상 **"다음 각 목"이라고 말하는 호만** 목을 가진다. 그러니 그런 호에, 목 묶음(목번호가 `가.`로 리셋되는 단위)을 순서대로 매칭하면 된다. 위 예시에서도 1번 호가 "다음 각 목"이라 말하고 2번은 안 하니까 정확히 붙는다.

**결정(왜) — 채택 전에 측정했고, 측정 결과로 기각했다.**
4개 법령(조특법·소득세법·소득세법 시행령·근퇴법 시행령) **238개 항에 대고 실측 → 80.3%만 일치(191/238), 47건 불일치.**

80.3%는 관점에 따라 "꽤 맞는다"로 읽을 수도 있다. 하지만 이 프로젝트에서는 **"5건 중 1건을 조용히 틀리게 붙인다"** 로 읽어야 한다. 틀린 20%는 에러를 내지 않고 그냥 잘못된 조문 구조가 되며, 그 위에 세법 값이 올라간다.

→ **기각.** 대신 소속 미상인 목의 첫 줄에 **`[각 목] ` 표식**만 달아 "이건 어느 호 소속인지 모른다"를 텍스트에 드러낸다. (뒤따르는 세목은 그 목의 하위라 소속이 명확하니 표식을 반복하지 않고, 호가 목을 **직접** 갖는 경우는 소속이 확정이라 표식을 안 단다.)

코드에는 `KNOWN-LIMITATION(코퍼스/조문구조)` 마커 + 사고 사례 + 80.3% 수치 + **업그레이드 경로**(조항호목 단위 API `lsNwJoListGuide` 계열이 부모 참조를 주는지 확인 → 준다면 교체하고 표식 제거)를 남겼다.

**검증.** 테스트 2번(소속 미상 목엔 표식), 3번(소속 확정 목엔 표식 없음)으로 계약 고정.

**배운 것.** ***틀린 구조를 주장하느니 모른다고 하는 편이 낫다.***
그리고 그 판단을 **감이 아니라 238개 항 실측으로** 내렸다는 게 핵심이다. "80% 정도면 되겠지"도, "위험하니 하지 말자"도 둘 다 감이다. 숫자를 재고 나서 **이 도메인에서 20% 오류가 무엇을 의미하는지**로 판단했다.

## 5. 7.31 — 작은 결정들, 각각의 이유

발표에서 한 줄씩 짚을 만한 것들.

**시행예정 → PROPOSED가 아니라 ENACTED.**
API의 `현행연혁코드`는 현행/시행예정/연혁 3종. 이름만 보면 "시행예정 = 아직 시행 안 됨 = PROPOSED" 같다. 하지만 **시행예정은 이미 국회를 통과해 공포된 법**이고 시행일만 미래다. 사양의 `PROPOSED`는 **국회 통과 전 개정안**을 뜻한다(그래서 순서 2의 R61이 "PROPOSED를 계산 경로에서 인출 금지"로 막는다). 여기서 PROPOSED로 뒀다면 **시행예정 법령이 R61에 걸려 영원히 계산에 못 들어가는** 엉뚱한 결과가 났을 것이다.
→ status는 ENACTED로 두고, 조회일 기준 유효성(`valid_from <= query_date`, 사양 §5.1)이 알아서 거르게 한다. **참고로 법제처 API는 공포된 것만 주므로 이 경로에서는 PROPOSED가 나올 수 없다.**
*배운 것: 이름이 비슷한 열거값을 이름만 보고 매핑하지 않는다. 그 값이 하류에서 어떤 규칙에 걸리는지까지 따라가 본다.*

**메타데이터는 검색 응답에서, 본문의 `기본정보`에서 안 가져온다.**
검색 응답 key(`법령명한글`·`법령일련번호`·`법령구분명`·`현행연혁코드`·`공포일자`·`시행일자`)는 실호출로 검증했지만 `기본정보` 하위 key는 검증하지 않았다. **추측한 key로 읽으면 에러가 아니라 값이 조용히 빈 문자열이 된다** — 이 프로젝트에서 제일 나쁜 실패 형태다.
→ **추측한 key 0개.**
*배운 것: 외부 API에서 "아마 이 이름일 것" 은 코드에 넣지 않는다. 확인한 것만 읽는다.*

**해시는 조문 원문 텍스트에, `sha256Hex` 재사용.**
`@cube/numeric`의 `canonicalHash`는 ASCII key를 강제한다(순서 2 R31의 그 규칙). 법제처 응답은 한글 key라 통째로는 해싱이 불가능하다. 새 해시 유틸을 만들 수도 있었지만, **이미 export되어 있는 `sha256Hex`를 원문 텍스트에 걸었다.** 어차피 원문 대조의 대상도 텍스트다.
→ **새 해시 코드 0줄.**
*배운 것: 제약(ASCII key)을 우회할 새 코드를 짜기 전에, 제약이 걸리지 않는 대상(텍스트)으로 문제를 옮길 수 있는지 먼저 본다.*

**새 의존성 0.**
`type=JSON` → XML 파서 불필요. Node 내장 fetch. `--env-file-if-exists` → dotenv 불필요.
*배운 것: 라이브러리를 넣기 전에 "런타임이 이미 하나?"를 먼저 묻는다.*

**`LAW_OC`는 경고하되 하드 실패시키지 않는다.**
OC는 비밀키가 아니라 **신청자 식별자**(쿼리스트링 평문)다. 그래도 계정 교체를 코드 수정 없이 하려고 `.env`에 뒀다. 미설정/`test`면 샘플 계정으로 진행하되 **눈에 띄게 경고**한다.
왜 하드 실패가 아닌가: **샘플 계정으로 개발이 가능해야 OC 발급을 기다리며 막히지 않는다.** 왜 그래도 경고는 크게: 조용히 넘어가면 샘플 계정으로 본 수집을 해버린다.
*배운 것: "막을 것"과 "알릴 것"을 구분한다. 전부 막으면 개발이 멈추고, 전부 통과시키면 사고가 난다.*

**`$pending` 블록 — 못 얻는 것을 명시적으로 적는다.**
이 API로 못 얻는 5종(퇴직연금감독규정·국세청 예규·금감원 통합연금포털·단수처리 법령·통계청 생명표)을 `targets.json`에 **적어뒀다.** 사양 §0-A.7("비포함 항목을 조용히 빼지 마라")의 정신을 데이터 수집 단계로 옮긴 것.
*배운 것: 커버리지 공백은 없애지 못해도 최소한 보이게는 만든다. 안 적으면 다음 사람이 "다 수집됐구나"로 오해한다.*

## 6. 7.31 — 원문을 손에 쥐자 바로 두 가지가 잡혔다

수집 자체보다 **수집한 결과가 즉시 검증 장치로 일했다**는 게 이 세션의 예상 밖 소득이다.

**① 사양의 경고가 원문으로 확인됐다.**
사양 §12 v1.4에 "중요" 표시로 이런 게 있었다 — *"IRP 설정 자격을 '소득 유무'로 판정하는 것은 부정확할 가능성이 높다."* 사양을 쓴 사람의 **우려**였고, 근거는 붙어 있지 않았다.
→ `RETIRE_D_17`("개인형퇴직연금제도의 설정 대상") 원문을 열어보니 **법적 지위**로 정의하고 있었다: 자영업자 / 퇴직금제도 적용 근로자 / 공무원 / 군인 / 사립학교교직원 / 별정우체국 직원. **소득 언급이 전혀 없다.**
→ **사양의 우려가 맞았다.** 이제 이건 우려가 아니라 확인된 사실이고, 인용할 조문 id가 있다.

**② 오인용을 원문이 막았다.**
"중도인출"로 검색해 `RETIRE_D_14`를 IRP 근거 조문으로 인용할 뻔했다. 그런데 제목이 **"확정기여형퇴직연금제도의 중도인출 사유"** — **DC형**이었다. 실제 IRP 중도인출은 `RETIRE_D_18`("개인형퇴직연금제도의 급여 종류별 수급요건 및 중도인출").
→ **원문이 파일로 있었기에 잡혔다.** 검색 결과 제목만 보고 인용했으면 DC형 규정을 IRP 근거로 삼는 사고가 났고, 그건 "그럴듯하게 틀린 답"의 전형이다.

**배운 것.** *원문을 손에 갖고 있는 것 자체가 검증 장치다.* RAG를 붙이기 전에도, 사람이 파일을 열어보는 것만으로 사양의 가설이 확인되고 오인용이 잡힌다. **근거를 가까이 두면 틀릴 기회가 줄어든다.**

## 7. 오늘 하지 않은 것 — 그리고 왜 하지 않았나

발표에서 **반드시 같이 말해야 하는 부분**이다. "다 했다"고 말하면 첫 질문에서 무너진다.

**파라미터 추출 0건.** 원문에 "100분의 9", "400만원", "200만원"이 **눈에 보인다.** 옮겨 적으면 정책 팩이 반쯤 채워진다.
→ **일부러 안 했다.** CLAUDE.md 절대 규칙 0·1: 모든 정책 팩에는 `pack_kind`가 있어야 하고, `VERIFIED_LAW`를 선언하려면 전 규칙이 `review.approved`(Maker–Checker)를 통과해야 한다. **값을 옮기는 건 코드 작업이 아니라 승인 절차가 붙은 작업**이다.
→ **오늘 한 건 "증거 확보"지 "판결"이 아니다.**

**그 외 남은 것:** RAG 색인 미착수 · ADMIN_GUIDANCE(국세청 예규·금감원 통합연금포털) 미수집(API 범위 밖) · 퇴직연금감독규정 미수집(`target=admrul`) · 세액 단수처리 법령은 **정확한 법령명조차 미확정** · 목의 소속 호 미해결(표식만) · `법령.부칙` 미수집(본칙만) · **§12 커버리지를 기계적으로 검증하는 테스트 없음**(이번엔 일회성 스크립트로 눈 확인).

**정직 메모:** OC 교체 재현성 검증에서 기록한 `TAXEX_91_18` 해시가 **현재 파일의 해시와 다르다.** 그 검증이 버그 3(세목 유실) 수정 **이전** 시점이라 원문이 달라진 것으로 보이지만, 재실행으로 확인하지 않았다 — 세목 수정 후 버전으로 **1회 재실행해 다시 고정해야 한다.**

**배운 것.** *"할 수 있는데 안 한 것"과 "못 한 것"을 구분해서 말한다.* 파라미터 추출은 전자고, 목 소속 호는 후자다. 둘을 뭉뚱그리면 어느 쪽도 신뢰를 못 얻는다.

## 8. 다음 단계 — RAG 색인 (미션 1 본체)

이제 색인할 원문이 있다.

- **Step A** — 조문 청킹 + 임베딩 색인
- **Step B** — BM25 2-gram + 벡터 하이브리드 (한국어 법령은 어휘 일치가 강해 BM25가 잘 듣고, 벡터는 "서민형"↔"총급여 5천만원 이하" 같은 어휘 불일치를 잡는다)
- **Step C** — reranker. **없이 먼저 써보고 나쁜 걸 확인한 뒤** 붙인다 — 효과를 눈으로 본 부품만 넣는다
- **Step D** — Fact Resolver + `FactAnswerManifest`. **검증 코드는 `packages/policy/src/manifest.ts`에 이미 있다**(순서 2의 R57~R60: `REGISTRY_RESOLVED_FACT`면 `resolvedRuleIds` 필수, `UNMODELED_OFFICIAL_SOURCE`면 빈 배열, 출처-해시 짝 일치)

**착수 전 결정 필요:** 임베딩 API 키.
**인프라 판단:** 규모가 작아(조문 1,849 → 청크 3~4천) **벡터 DB 없이 메모리 brute-force 코사인으로 충분**하다. 3~4천 벡터 전수 비교는 밀리초 단위다. 없어도 되는 인프라는 안 만든다.

## 10. 7.31 (밤) — ★ "안 되게 만드는 것"이 기능이다: 승인 게이트와 Router

### 계기
AI 가 만든 정책 팩 초안을 승격시키려는데 로더가 막았다. `ROUNDING_ENUM_INVALID`.

### 문제
반올림 사양(어느 단계에서 · 어떻게 · 몇 원 단위로 끊나)은 **조문에 안 적혀 있는 경우가 대부분**이다. 절대 규칙 1이 "값을 지어내지 말고 실패 경로를 구현하라"고 하니 `<원문 대조 후 기재>` 를 넣었는데, 그 필드가 enum 이라 **스키마 검증이 먼저 터졌다.**

### 진단 — 거절은 맞았는데, 이유가 틀렸다
막힌 것 자체는 옳다. 문제는 **로더가 댄 이유**다. 진짜 원인은 "아직 확정 안 된 값"인데 로더는 "enum 위반"이라고 말한다. 사람은 그 메시지를 읽고 enum 목록을 고치러 갈 것이다 — 엉뚱한 데를.

### 결정
세 갈래가 있었다. (a) 스키마 enum 을 느슨하게 (b) 초안에만 placeholder 허용 (c) 필드를 아예 빼기.
**(c).** 이유: 거절 매트릭스 R15 가 이미 "일부만 있으면 거절"이라고 정해뒀으니 **전부 없는 것은 유효**하다 — 새 규칙을 만들 필요 없이 **이미 있는 규칙이 답을 갖고 있었다.** (a)·(b)는 검증을 약하게 만들어 값이 새는 구멍이 된다.

### 검증
승격 통과. 초안 팩은 여전히 `resolveEffect` 에서 `UnverifiedPolicyError` 를 던진다 — **로드는 되지만 계산엔 못 들어간다**는 원래 의도 그대로.

### 배운 것
**거절 메시지가 원인을 정확히 지목하지 못하면, 거절이 있어도 사람이 엉뚱한 데를 고친다.** "막았다"로 끝나는 게 아니라 "왜 막혔는지 정확히 말했다"까지가 방어다.

## 11. 7.31 (밤) — ★ Router: 부탁하지 말고 배선으로 막아라

### 문제
사양 §1.2 는 미모델링 답변의 **개인 적용 금지**를 못 박는다. 그런데 "나 연봉 6천인데 IRP 얼마 넣어야 돼?" 를 FACT 엔진에 넣으면, LLM 은 조문을 읽고 **개인에게 맞춘 답을 쓰려고 한다.** 프롬프트에 "그러지 마"라고 적는 건 사후 방어다.

### 결정 — 그 질문이 엔진에 도달하지 않게
LLM 없이 규칙 기반. 이유 셋:
1. **재현성(§1.3)** — 같은 질문은 항상 같은 분기로 가야 한다. LLM 분류기는 그 보장이 없다.
2. **비용** — 라우팅에 콜을 쓰면 걷어낼 질문에 돈을 쓰는 셈이다.
3. **손해가 비대칭** — PLAN→FACT 로 새면 §1.2 가 뚫린다. FACT→PLAN 으로 잘못 보내면 안내가 나가고 다시 물으면 된다. 그래서 **PLAN 쪽으로 기울였다.**

### 두 번 틀렸고 둘 다 테스트가 잡았다

**(1) 한국어 부분문자열.** `내`·`제`·`저` 를 `includes` 로 잡으니 **제55조**·**국내**·**저축**·**내국법인**이 전부 PLAN 으로 갔다. → 조사까지 붙은 토큰(`내가`·`제가`·`저는`)만.

**(2) 나이 수치.** `40세 이상 가입 제한이 있나` 가 PLAN 으로 갔다. 그런데 이건 **조문의 가입 요건**을 묻는 FACT 질의다. 원인을 파보니 재미있었다 — **나이는 조문에도 흔히 나오는 수치**고, **연봉·월급 액수는 조문이 절대 쓰지 않는 표현**이었다. 그래서 나이는 "약한 신호"(2개 이상 겹칠 때만), 연봉은 "강한 신호"로 갈랐다. 나이도 `35살인데` 처럼 **상황 서술 어미**가 붙으면 강한 신호로 승격.

### 검증
고정 케이스 22건. 실측으로 **PLAN 질의는 검색·LLM 을 아예 타지 않는다(API 콜 0회)** 는 것도 확인.

### 배운 것
**막는 방법은 부탁이 아니라 배선이어야 한다.** 그리고 **오분류를 고칠 땐 "왜 이 표현은 조문에 나오고 저 표현은 안 나오는가"를 물어야** 규칙이 원리를 갖는다 — 케이스를 하나씩 특례로 빼면 목록이 아니라 누더기가 된다.

## 12. 7.31 (밤) — ★ 계산 금지를 리뷰가 아니라 grep 으로

### 결정
`packages/factui/` 는 `node:http` + 정적 파일. **React/Vite 없음, 새 의존성 0.**
렌더는 **서버의 순수 함수 하나**. 브라우저 JS 는 fetch + `innerHTML` 이 전부(35줄), 원문 접기는 `<details>` 가 네이티브로.

이렇게 하니 부수 효과가 둘 생겼다 — ① 계산 금지 grep 이 파일 몇 개만 훑으면 되고 ② **합성 스탬프가 DOM 에 실제로 있는지 브라우저 없이 문자열로 확인**된다.

### 검사기를 만들면서 배운 것: 오탐과 미탐은 같이 봐야 한다

오탐 2건이 나왔고 **둘 다 진짜 오탐**이었다 — `127.0.0.1` 의 `0.0` 이 세율로, 예시 질문 칩 `"IRP 납입한도"` 가 하드코딩 값으로. 여기서 그냥 좁히기만 했으면 검사가 약해졌을 것이다. 좁히는 김에 **"그럼 이건 잡히나?"** 를 물어 두 건을 더 찾았다:
- `const nonTaxLimit = 20000000;` — 산술이 없어도 세법스러운 이름 + 큰 수 = 하드코딩
- `base * 12` — 이름만 봐선 모를 계산. UI 는 어차피 계산하면 안 된다

그리고 **탐지기 자신을 검증하는 테스트**를 넣었다. 미끼(`income * 0.15`)를 심어 잡히는지 본다.
*검사기가 고장 나면 본 테스트는 매일 조용히 초록불을 켠다.*

### 실제로 돌린 것
`"IRP 연간 납입한도가 얼마인가"` → **1천800만원 + ISA 전환금액 + 주택차액** 세 갈래가 조건(60세 이상, 1회 한정)까지 붙어 나왔다. 근거 2건에 시행일·해시·**원문 전문 접기**. 매니페스트에 `정책 스냅샷 = NO_APPROVED_PACK`. 위조 인용 0건.

**첫 시도는 답이 갑자기 가업승계 증여세 얘기를 했다.** curl 이 한글을 깨뜨려 엉뚱한 질의가 간 것이었다. → *답이 이상하면 먼저 "내가 뭘 보냈는지"를 의심한다.*

### 배운 것
**의존성을 안 늘리는 게 기능이다.** React 를 안 써서 `app.js` 가 35줄이고, 그래서 "UI 는 계산 안 한다"를 **파일 몇 개 grep 으로 증명**할 수 있다. 큰 프레임워크였으면 같은 주장을 하려면 훨씬 많은 코드를 훑어야 했다.
