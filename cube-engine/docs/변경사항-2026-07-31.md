## 1. 신규 패키지 `packages/corpus/` — 왜 별도 패키지인가

**무엇:** 법제처 원문을 받아 `SourceSnapshot`으로 굳히는 수집 계층. `@cube/numeric`만 참조하고 `@cube/policy`·`@cube/engine`은 참조하지 않는다.

- **왜 policy 안이 아니라 별도 패키지인가:** policy는 **로딩·검증 계층**이고 corpus는 **획득 계층**이다. corpus가 policy를 참조하면 "원문을 받는 코드"가 "정책 팩을 해석하는 코드"에 묶여, 원문 수집이 정책 스키마 변경에 흔들린다. 방향은 나중에 policy → (사람 승인) → 팩으로 흐르지 코드 의존이 생기지 않는다.
- **레포 컨벤션 준수:** `tsc -b`, `node --test "dist/test/**/*.test.js"`, ESM(`"type": "module"`), `private: true`. 기존 패키지와 스크립트 이름·형태가 같다.

### 1.1 `package.json`
```
build   : tsc -b tsconfig.json
test    : tsc -b tsconfig.json && node --test "dist/test/**/*.test.js"
collect : tsc -b tsconfig.json && node --env-file-if-exists=../../.env dist/scripts/collect.js
```
- `--env-file-if-exists` = Node 내장. **dotenv 의존성을 추가하지 않기 위해서**이고, `.env`가 없어도 스크립트가 죽지 않게 하려고 `-if-exists` 쪽을 골랐다(OC 없으면 샘플 계정 경고 후 진행).
- `dependencies`: `@cube/numeric` 하나. 외부 의존 0.

### 1.2 `tsconfig.json`
- `tsconfig.base` 상속 + `references: [{ path: "../numeric" }]`. 레포의 project references 체인에 그대로 편입.

### 1.4 `src/types.ts`
- `SourceSnapshot` — lawName / lawId / mst / authorityType / lifecycleStatus / promulgatedAt / enforcedAt / collectedAt / sourceUrl / articles[]
- `ArticleSnapshot` — sourceId / articleNo / articleSubNo / title / text / validFrom / textHash
- `AuthorityType`(STATUTE·DECREE·RULE) / `LifecycleStatus`(ENACTED·REPEALED…) / `CollectTarget`
- 필드명은 사양 §5.1의 `authority.type`·`lifecycle.status`·`temporal.valid_from`에 1:1로 대응시켰다(임의 개명 금지 규칙).

### 1.5 `src/json.ts` — 외부 JSON 방어적 읽기
- `asRecord(value, what)` / `asArray(value)` / `str(rec, key)`. 전부 **경로 이름(`what`)을 에러 메시지에 넣는다** — 법제처 응답 구조가 바뀌었을 때 "어느 계층에서 깨졌나"가 바로 나와야 진단이 된다.
- `asArray`는 단일 객체도 1원소 배열로 정규화한다(법제처는 원소가 1개면 배열을 벗겨서 준다).

### 1.6 `src/lawApi.ts` — API 클라이언트
- `resolveOc()` — `LAW_OC` env 읽기. 미설정 또는 `test`면 **눈에 띄게 경고하되 하드 실패시키지 않고** `"test"`(샘플 계정) 반환.
  - 왜 하드 실패가 아닌가: 샘플 계정으로 개발·검증이 가능해야 OC 발급을 기다리며 막히지 않는다. 대신 조용히 넘어가면 샘플 계정으로 본 수집을 해버리므로 경고는 크게.
  - 왜 `.env`인가: `LAW_OC`는 **비밀키가 아니라 신청자 식별자**(쿼리스트링에 평문으로 나간다). 그럼에도 계정 교체를 코드 수정 없이 하려고 env에 뒀다.
- `searchLaw(oc, lawName)` → `lawSearch.do?target=law&type=JSON&query=…&display=100` → `LawIndexEntry[]`
  - 뽑는 key(전부 **실호출로 검증**): `법령명한글`·`법령ID`·`법령일련번호`(=MST)·`법령구분명`·`현행연혁코드`·`공포일자`·`시행일자`
- `fetchLawBody(oc, mst)` → `lawService.do?target=law&type=JSON&MST=…`
  - **JO를 주지 않아 전 조문을 한 번에 받는다.** 주석에 이유 2개를 남김(재수집 없음 / 사양 §1.2 FACT 2클래스 대응).
- `callApi` 공통 처리: HTTP 비정상 → throw. **HTTP 200인데 JSON이 아니면** OC 인증 실패·미신청 target을 의미하므로 url + body 앞 200자를 붙여 throw(로그인 HTML이 200으로 돌아오는 경로가 실제로 있다).

### 1.7 `src/parse.ts` — 응답 → 스냅샷 (순수 함수, 네트워크 없음)
네트워크를 분리했기 때문에 fixture만으로 13개 테스트가 돈다.

| 함수 | 하는 일 | 핵심 결정 |
|---|---|---|
| `toLocalDate` | `"20260101"` → `"2026-01-01"` | KST LocalDate, **UTC 변환 없음**(CLAUDE.md 규칙 6). 형식 위반은 throw |
| `mapAuthorityType` | 법령구분명 → STATUTE/DECREE/RULE | 모르는 구분명은 **거절**. 충돌 서열의 근거값이라 틀리면 상위법이 하위법에 밀린다 |
| `mapLifecycle` | 현행연혁코드 → ENACTED/REPEALED | **"시행예정"을 PROPOSED로 두지 않았다** — 이미 공포된 법이고 시행일만 미래이므로 ENACTED. 조회일 기준 유효성(`valid_from <= query_date`)이 알아서 거른다. 사양의 PROPOSED는 국회 통과 전 개정안이고, 법제처 API는 공포된 것만 준다 |
| `textsOf` | `…내용` 값 → 문자열 조각 배열 | **재귀 평탄화.** 중첩 배열로 오는 세목을 살린다(버그 3) |

- **정확일치 선택**(`pickEntry`) — 부분일치 금지. 정확일치가 없으면 후보 8개를 찍어주고 throw("targets.json의 lawName을 아래 중 하나로 맞춰라"). 같은 이름이 여러 판이면 `현행`을 고른다.
- 인자로 법령명을 주면 일부만 수집 가능(`npm run collect -w @cube/corpus -- 소득세법`).
- **실패 요약 + `process.exitCode = 1`** — 6건 중 5건이 실패해도 조용히 성공 코드를 내지 않는다. (버그 1이 드러난 경로가 정확히 이것이다.)
- 파일 상단 주석에 못 박음: *"산출물은 원문 스냅샷이며 정책 팩이 아니다. 세율·한도를 뽑아 정책 팩으로 만드는 건 다음 단계이고 사람 승인이 필요하다(절대 규칙 0·1)."*

## 2. 발견한 버그 3개 — 전부 "에러를 내지 않는" 종류

### 버그 1 — 전문/조문 혼입으로 `source_id` 충돌
- **증상:** 첫 수집에서 **6건 중 5건 실패.**
- **원인:** 응답의 `조문여부` 필드가 `"조문"`(조특법 기준 458개) / `"전문"`(35개)으로 갈린다. `"전문"`은 "제1장 총칙" 같은 **편·장·절 표제**인데 **자기 번호가 없어서 뒤따르는 조문의 번호를 그대로 달고 온다**("제1장 총칙"이 조문번호 `"1"`). 그래서 제1조와 `source_id`가 충돌했다.
- **초기 휴리스틱이 안 먹힌 이유:** "조문번호가 비면 건너뛴다"로 짰는데, 전문은 번호가 **비어 있지 않고 남의 번호를 달고 있었다.**
- **수정:** 추정 대신 **명시 필드**로 — `if (str(rec, "조문여부") !== "조문") continue;`
- **부칙 확인:** 부칙은 `법령.조문`이 아니라 `법령.부칙`에 따로 있어 애초에 안 섞인다.
- **★ 이 버그의 진짜 교훈:** 첫판에 유일하게 "성공"한 `RETIRE_D`(79 조문)도 **충돌만 안 났을 뿐 같은 오염 위험**에 놓여 있었다. **충돌 시 "그냥 덮어쓰기"로 짰다면 6개 전부 조용히 성공했을 것이고, 오염된 코퍼스 위에 정책 팩을 쌓았을 것이다.** 실패 5건은 방어 장치가 일한 결과다.

### 버그 2 — 조문 첫 문장이 맨 뒤로 밀림
- **증상:** **모든 조문**에서 조문 헤더("제91조의18(개인종합자산관리계좌에 대한 과세특례)")가 항·호 **뒤**에 붙었다.
- **원인:** 응답 최상위 key 순서가 `조문번호 | … | 조문키 | 항 | 조문내용 | 조문제목 | …`이다. key 순서대로 훑는 방식이 그대로 순서를 물려받았다.
- **수정:** key 순서 의존 폐기 → `articleChunks`에서 **명시적 조립**(조문내용 → 항 → 호 → 목).

### 버그 3 — 세목 유실 (가장 위험했음)
- **증상:** 없음. 저장은 정상적으로 되고 원문도 "그럴듯"했다.
- **원인:** `목내용`이 문자열이 아니라 **배열의 배열**로 오는 경우가 있다. 목 아래 `(1)(2)(3)` 세목이 중첩 배열에 들어 있다. 실례 — **소득세법 시행령 §20 ① 나목**(일용근로자에서 제외되는 업무 목록).
- **범위:** **조립 함수와 검산 함수 둘 다** 이걸 버리고 있었다. 즉 검산도 같은 눈으로 세고 있어서 개수가 맞아떨어졌다.
- **수정:** `textsOf()` 재귀 평탄화(문자열·숫자·중첩 배열 전부 처리) + `countTextNodes`도 같은 함수로 세게 통일.
- **효과:** **되찾은 원문 6만 5천여 자** — 1,852,000자 → **1,917,666자.**
- **어떻게 잡혔나:** **자체 검산 장치**(조립한 조각 수 vs 응답의 `…내용` 노드 수 비교, 불일치 시 throw)가 없었으면 절대 못 찾았다. 그 검산은 처음엔 **내 비교 로직의 버그**를 먼저 잡아냈다 — ① 줄 수 vs 조각 수 혼동(원문 문자열 안에 줄바꿈이 들어 있는 조문이 실제로 있다) ② 빈 목에 `[각 목]` 표식만 붙어 **유령 조각**이 생김. 그걸 고치고 나서야 진짜 원인이 드러났다.

## 4. 측정 후 기각한 heuristic — 목의 소속 호

**문제:** API가 `목`을 `호`의 자식이 아니라 **`항`의 형제**로 내려준다. 한 항의 여러 호에 걸린 목이 하나의 평평한 배열로 합쳐지고 부모 호 참조가 없다. 실측 — **조특법 §91의18 ③ = 호 5개에 목 9개**, 목번호가 `가·나·다` 다음 또 `가·나·다·라·마·바`로 리셋된다.

**그냥 이어붙이면 목이 마지막 호에 속한 것처럼 읽힌다.** 실제 사고 사례(ISA 비과세 한도, §91의18 ②):
```
1. 다음 각 목의 어느 하나에 해당하는 경우: 400만원   ← 가·나·다는 여기 소속
2. 제1호에 해당하지 아니하는 자의 경우: 200만원
가. 직전 과세기간의 총급여액이 5천만원 이하인 거주자…   ← 2번 뒤에 붙음
```
읽으면 "총급여 5천만원 이하 → 200만원"으로 **뒤집힌다.** 실제로는 400만원(서민형)이다. 사양 §12에서 **1순위**로 지정된 파라미터가 정반대가 되는 상황.

**heuristic 후보:** 법률 작성 관행상 "다음 각 목"이라고 말하는 호만 목을 가지므로, 그런 호에 목 묶음(목번호가 `가.`로 리셋되는 단위)을 순서대로 매칭한다.

**실측:** 4개 법령(조특법·소득세법·소득세법 시행령·근퇴법 시행령) **238개 항 → 80.3% 일치(191/238), 47건 불일치.**

**결정:** **기각.** 5건 중 1건을 조용히 틀리게 붙이는 셈이다. 대신 소속 미상인 목의 첫 줄에 **`[각 목] ` 표식**만 달아 "어느 호 소속인지 모른다"를 텍스트에 드러낸다. 뒤따르는 세목은 그 목의 하위라 소속이 명확하니 표식을 반복하지 않는다. 호가 목을 **직접** 갖는 경우는 소속이 확정이므로 표식 없이 붙인다.

**코드 마커:** `parse.ts`의 `UNATTACHED_MOK` 주석에 `KNOWN-LIMITATION(코퍼스/조문구조)` + 사고 사례 + 80.3% 수치 + **업그레이드 경로**(조항호목 단위 API `lsNwJoListGuide` 계열이 부모 참조를 주는지 확인 → 준다면 교체하고 표식 제거).

> 원칙: **틀린 구조를 주장하느니 모른다고 하는 편이 낫다.**

## 정직 메모 마감 (같은 날 후속)

문서를 쓰면서 남긴 미검증 3건을 그대로 두지 않고 당일 닫았다. **셋 다 "나중에 하면 더 비싸지는" 종류**여서다 — 특히 ②는 발표에서 인용할 숫자가 틀린 채로 남을 뻔했다.

### 정정 — OC 재현성 해시

| | 이전 기록 | 정정 |
|---|---|---|
| `TAXEX_91_18` 해시 | `59f768813c327bcd…` | **`61495aafdc60f14953b612e6a9fc6efaa742acc27e5a5b699bb740e5f79e87ca`** |
| 그 해시의 원문 길이 | 3,668자 | **3,740자** (세목 복구분 +72자) |
| 대조 범위 | ISA 조문 1건 | **전 조문 1,849건** |

**틀린 게 아니라 낡은 것이었다.** `59f768…`은 버그 3(세목 유실) 수정 **이전** 원문의 해시다. 세목을 되찾으면서 원문이 바뀌었으니 해시도 바뀌는 게 정상이다 — 재현성이 깨진 게 아니라 **원문이 개선된 것.** 다만 문서에 남은 숫자가 낡았다는 사실 자체는 결함이므로 재실행해 고정했다.

**재검증 절차 (재현 가능):**
1. 현재 파일(`LAW_OC=harrypobi`)의 조문 1,849개 `sourceId → textHash` 를 전부 덤프
2. `LAW_OC=test`(법제처 샘플 계정)로 `npm run collect -w @cube/corpus` 재실행 — 경고 출력으로 override 적용 확인
3. 전수 대조 → **동일 1,849 / 불일치 0 / 사라짐 0 / MST 변화 없음**
4. `sourceUrl` 만 `OC=harrypobi` ↔ `OC=test` 로 다름 (계정 식별자가 URL 에 실리므로 정상)
5. 원래 OC 로 재수집해 복구, 테스트 17/17 통과 확인

**결론:** 계정이 달라도 같은 MST 면 원문이 바이트 동일하다. **판(version)을 결정하는 건 계정이 아니라 MST 다.** 이전 기록은 ISA 1건만 대조했는데 이번엔 전수라 근거가 더 강해졌다.

### 검사기를 좁히면서 같이 넓힌 것 (no-computation)

| 패턴 | 방향 | 이유 |
|---|---|---|
| `\b0\.\d+` → `(?<![\d.])0\.\d+(?![\d.])` | 좁힘 | `127.0.0.1` 의 `0.0` 이 세율로 잡혔다 |
| `한도\|세율\|…` → 그 어휘 **근처에 숫자가 있을 때만** | 좁힘 | 예시 질문 칩 `"IRP 납입한도"` 가 하드코딩 값으로 잡혔다. 어휘가 아니라 **값**을 잡아야 한다 |
| `(rate\|tax\|limit\|…)\w*\s*[:=]\s*\d{4,}` | **넓힘** | 산술이 없어도 `const nonTaxLimit = 20000000;` 은 하드코딩된 세법 값이다 |
| `[A-Za-z_$)\]]\s*[*/]\s*\d` 등 | **넓힘** | `base * 12` — 이름만 봐선 세법 값인지 모르는 계산. UI 는 어차피 계산하면 안 된다 |
