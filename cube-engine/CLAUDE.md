## 절대 규칙 (위반 = 즉시 실패 처리)
0. **정책 팩 종류를 반드시 명시하라.** 모든 정책 팩에 `pack_kind`가 있어야 한다 — `VERIFIED_LAW`(원문 대조·승인 완료) / `SYNTHETIC_DEMO`(알고리즘 검증용 합성 값) / `UNVERIFIED_DRAFT`(초안, 계산 시 `UnverifiedPolicyError`). `SYNTHETIC_DEMO`로 계산한 결과의 모든 출력에는 **"합성 세법 값 · 실제 세법이 아님" 스탬프를 강제 부착**하라. 스탬프 없이 합성 값 결과를 내보내는 코드는 즉시 실패로 취급한다.
1. **세법 값 하드코딩 절대 금지.** 세율·한도·경계값·반올림 사양은 코드·테스트·주석·기본값 어디에도 리터럴로 쓰지 마라. 모든 값은 정책 팩(source + review.approved 필수)에서만 온다. 임시값이 필요하면 값을 지어내지 말고 `UnverifiedPolicyError`를 던지는 실패 경로를 구현하라. "TODO: 나중에 15%로 교체" 같은 placeholder 숫자도 금지다.
2. **금액에 부동소수점 금지.** 도메인 내부는 `KRW = bigint`, 경계(JSON/DB)는 `KRWString`(10진 정수 문자열, 선행 0·-0 금지). 세율은 `DecimalRate`(유리수). 사양 §5.2의 직렬화·해시 절차를 따르라.
3. **계산·판정 코드 경로에서 LLM 호출 금지.** LLM은 파서(비권위적 추출)와 렌더러(승인 claim 내 설명)에만 존재한다. Eligibility, Tax Calculator, Projection, Optimizer 어디에서도 LLM API를 호출하지 마라.
4. **계좌명 분기 금지.** `if (accountId === "IRP")` 류의 코드는 금지. 모든 계좌 로직은 MechanismHandler를 통해서만.
5. **불변식 위반 시 부분 동작 금지.** 커버리지 검사 실패, 의존성 순환, 정렬 미결정, PRIMARY source 부재 → 부분 계산이 아니라 명시적 로딩 거절/에러.
6. **시간 상태 저장 금지.** `CURRENT` 같은 상태를 데이터에 쓰지 말고 조회 시점에 계산(사양 §5.1). 날짜는 KST `YYYY-MM-DD` LocalDate — UTC 변환 금지.
7. **독립 기준 계산기(Python)는 프로덕션 코드를 import하지 않는다.** 같은 명세, 독립 구현, 중간값까지 differential 비교.

## v1.3 추가 규칙
8. **UI에서 계산 금지.** 여력·절세액·필요 저축액·우선순위는 전부 엔진 출력만 표시한다. 화면에 산식을 넣거나 우선순위를 상수로 박지 마라 (사양 §5.8 Surface Binding).
9. **마이데이터는 어댑터+합성 fixture만.** 실연동 코드·실제 토큰·실데이터 접근 금지. fixture는 표준 규격 필드명을 그대로 쓴다 (사양 §5.7).
10. **목표는 계약이다.** `RetirementIncomeGoal`(은퇴 시작 나이 + 지급 종료 시점 + 월 세후 실질 목표액 + incomeRule)을 받지 않고 계산하지 마라. 은퇴 시점 자산총액을 최종 목표로 삼는 코드도 금지 — 자산총액은 중간값이다.
10-a. **목표 충족은 평균이 아니라 최저 보장이다.** `minimumIncomeCoverageRatio >= 100%`가 아니면 "달성"으로 표시하지 마라.
10-b. **납입액은 두 숫자다.** `monthlyGrossContribution`(계좌 입금액)과 `monthlyNetOutOfPocketCost`(실질 부담)를 항상 함께 산출하고, 최적화 목적함수는 후자다.
10-c. **CUBE 목표는 포트폴리오 현금흐름이다.** 국민연금 등 외부 소득을 임의로 가정해 차감하지 마라 — 사용자가 입력한 값만 단순 차감한다.
11. **성향은 점수화 금지.** PreferenceProfile로 분기해 병렬 실행하고, 프로필 간 순위를 매기지 마라 (사양 §6.1.7).

## 설계 훼손 금지 (사양 부록 B 필독)

코드를 개선하려는 선의로 아래를 건드리면 설계가 파괴된다. 각 항목은 6라운드 검토에서 기각된 대안이거나 보장의 근거다.

- **`HOLD_CASH`를 액션 공간에서 제거하지 마라.** 쓸모없어 보이지만 "저축 증가 → 결과 비악화"의 구조적 보장이며, 모드 B 이분탐색의 전제다. 제거하려면 `boundedGridSearch()` 폴백이 필수.
- **후보 전수 열거를 탐욕 루프로 치환하지 마라.** 탐욕은 이미 검토 후 기각됐다 — 시간 순서 전략(ISA 만기 전환 등)을 생성하지 못하고 최적성도 성립하지 않는다. 성능 문제는 v2의 DP/Solver로 해결하며 Optimizer Contract를 유지한다.
- **MoneyBucket을 단일 balance로 합치지 마라.** 수령 단계 과세가 재원별로 다르므로 계산이 원리적으로 틀린다.
- **이벤트 정렬 키를 줄이지 마라.** 같은 연도 내 순서가 비결정적이 되면 재현성이 깨진다.
- **적합성 점수·페널티 계수·"균형형" 같은 임의 가중치를 만들지 마라.** 근거를 제시할 수 없는 숫자는 판단에 들어가지 않는다.
- **프로필 병렬을 단일 대표안으로 축약하지 마라.** 프로필 간 순위를 매기는 코드는 금지다.
- **`rule_trace`·RunManifest 기록을 생략하지 마라.** 감사 가능성이 이 시스템의 존재 이유다.
- **`emitBreakpoints()`에서 경제적 경계점(비용·보수·한계가치 교차점·목표 충족 지점)을 빼지 마라.** 법적 한도만 방출하면 최적점을 놓친다 (사양 부록 B.4).
- **Optimizer 독립 참조 탐색기(brute-force)를 "중복"이라며 삭제하지 마라.** 후보 생성기의 누락을 잡는 유일한 장치다.
- **taxCharacter를 모를 때 하나의 숫자로 봉합하지 마라.** 신뢰도 4모드에 따라 범위 또는 계산 불가로 표기한다 (사양 §5.7.1).
- **비포함 항목을 조용히 빼지 마라.** 건강보험료 등 준조세·부채상환 비교·확률적 성공률·가구 합산은 v1 비계산 항목이며, 결과 출력에 **비포함 사실을 반드시 표기**해야 한다 (사양 §0-A.7). 표기 없는 "세후 금액"은 거짓이다.
- **예산 제약을 등식으로 쓰지 마라.** `총 납입액 ≤ 저축 가능액`(부등식)이 단조성 증명의 근거다. 등식으로 두면 slack이 사라져 이분탐색 전제가 깨진다 (사양 §6.1.6).
- **확률 표기 금지.** "성공률 N%" 같은 출력을 만들지 마라. 강건성은 시나리오 집합 충족 여부로만 표현한다.
- **일반계좌를 단일 잔액으로 다루지 마라.** `TaxableAccountLedger`(lot·취득원가·실현정책) 없이는 계획 매도 과세를 계산할 수 없다 (사양 §5.5).
- **`HOLD_CASH`를 일반계좌 현금 보유로 구현하지 마라.** 미납입 자본(시스템 외부 중립 버킷)이다. 계좌 내 현금으로 두면 이자가 금융소득 합산을 트리거해 단조성이 실제로 깨진다 (사양 §6.1.6).
- **guard가 미래 정보를 참조하게 하지 마라.** 결정 시점까지 관측된 상태만 참조한다. 시나리오 식별자·미래 수익률 참조는 사후 최적화이며 실행 불가능한 플랜을 만든다 (사양 §6.1.8 비선견성).
- **"평생"·"세후"·"실수령액"·"최소 저축액" 문구를 쓰지 마라.** 각각 "계획 종료 연령까지", "세금 반영 후", "지원 범위에서 가장 낮은"으로 (사양 §4.4).
- **외부 은퇴소득을 세무 상태에서 빼지 마라.** 최적화는 안 하지만 과세 합산에는 포함한다. 성격 미확인이면 세후 계산 불가로 표시 (사양 §0-A.4).
- **coverage ratio 분자를 입금액으로 계산하지 마라.** 원천징수와 세금준비금을 차감한 사용 가능 현금이다 (사양 §6.1.2).
- **또래 비교·사회적 증거형 문구를 생성하지 마라.** 기본안은 공개된 사전순위 규칙으로만 고른다 (사양 §6.1.5).
- **식별자에 한글을 쓰지 마라.** accountId·instrumentId·AssetClass 등 canonical JSON key가 되는 식별자는 ASCII `[A-Za-z0-9_]` 만 (예: `PENSION_SAVINGS`). 한글 명칭은 `displayName`에만 둔다.
- **표기법을 레이어 간에 섞지 마라.** TS 계층은 camelCase, 정책 팩 YAML은 snake_case. 정책 팩을 camelCase로 변환하지 마라 (사양 §5.2.1 네이밍 계약).

- 순서 3: MechanismInstance + phase/event 정렬 키 + 정렬 결정론 테스트 — **완료** (정렬 규칙 전체는 `docs/ORDER3-ORDERING-MATRIX.md`, 사양 모순은 `docs/ORDER3-OPEN-QUESTIONS.md`, 언어 중립 정답지는 `packages/engine/vectors/ordering.spec-derived.json`)
- **순서 4: 정책 코퍼스 원문 수집 (사람 작업, 코드와 병렬) ← 현재 단계**

- 순서 6.5: MyData Adapter + 합성 fixture (페르소나 3종)
- 순서 7: AI 층 (Router/Parser/Validation/확인 게이트/Claim Renderer) — E2E
- 순서 8: 데모 패키지

테스트 벡터에는 반드시 `sourceRuleIds` + `policyVersion`을 붙여라. 골든 테스트의 기대값도 정책 팩이 채워지기 전에는 실제 숫자를 넣지 말고 fixture 참조로 두라.

- 개인 축약어·비표준 마커를 만들지 마라. 레포 전체에서 grep 가능해야 한다.

## 테스트 정답지(oracle) 규약
- 정답지 파일은 `authority: "ORACLE"`, 회귀 감지용 생성 파일은 `authority: "NOT_AN_ORACLE"`로 헤더에 명시한다.
- 정답지는 **손으로 쓴다.** 구현 출력을 복사해 정답지로 만들지 마라 — 그 순간 버그가 사양으로 승격된다.
- 표준 함수(해시 등)의 기대값은 자기 출력이 아니라 **외부 공표 벡터**를 인용한다.
- 정답지는 사람 검토 서명을 받기 전까지 잠정이다. "골든 벡터가 있으니 검증됐다"고 주장하지 마라.

## 언어·컨벤션
- 코어: TypeScript (strict). 독립 계산기: Python.
- 모든 계산 함수는 순수 함수 + `rule_trace` 반환. 상태 변경은 `TransitionResult`로만.
- 사양에 정의된 인터페이스 이름·필드명을 그대로 사용하라 (임의 개명 금지).

## 하지 말 것
- 사양에 없는 기능 추가 (특정 종목 추천, 마이데이터 연동 등은 의도적 제외 항목)
- 세법 지식으로 빈 값을 "아는 값"으로 채우는 것 — 네가 아는 한도·세율이 최신·정확하다는 보장이 없고, 이 시스템의 존재 이유가 그 가정의 제거다
