## 1. 프로젝트 한 장 요약

**CUBE**는 절세 3종 계좌(ISA·연금저축·IRP)를 다루는 두 개의 엔진이다.

| | 미션 1 — FACT 엔진 | 미션 2 — PLAN 룰엔진 |
|---|---|---|
| 하는 일 | 법령 원문을 근거로 **인용된 답**을 준다 | 상황을 받아 **코드로 계산**한다 |
| 저장소 | **A4-RAG ← 이 문서** | `../A4-Logic/` |
| 분리일 | 2026-08-07 | 각각 완성 후 합침 |

두 엔진은 세법을 **각자 알지 않는다.** 동일한 Authoritative Policy Registry 하나를 공유하고(사양 §1.1, split-brain 금지), 모든 값은 원문 조문에 묶인다.

```
[법령 원문] → [Source Snapshot] → (사람 승인) → [Policy Pack] → ┬→ 미션 1 FACT 엔진 (A4-RAG)
 법제처 API    packages/corpus    Maker-Checker  packages/policy  └→ 미션 2 PLAN 룰엔진 (A4-Logic)
```

## 2. 왜 시작했나 — 해결하려던 문제

### 2.1 원 요구사항
`reference/과장님_cube.txt`가 요구사항의 원출처이고, 사양서 §0-A가 이를 해석한 결과다.

### 2.2 초기 PoC가 보여준 "하면 안 되는 방식"
`reference/_archive/code.html` · `test.js`는 초기 프로토타입이다. 이 코드는 **금지 패턴을 그대로 담고 있어서**, 오히려 이 프로젝트의 설계 근거가 됐다:

- 계좌별 **고정 세율표 하드코딩**
- 매매차익 **연 5% 고정 가정**
- 적합성 점수 50/70/90 — **근거 없는 임의 가중치**
- 한도 검사를 `한도 > 0`으로만 수행

→ CLAUDE.md는 이 파일을 "확장·리팩터링하지 말라"고 명시한다. UI 레이아웃과 테스트 러너 구조만 참고 가능.

### 2.3 진짜 문제
세법 챗봇에서 **가장 위험한 실패는 크래시가 아니라 "그럴듯하게 틀린 값"**이다.

- 틀린 숫자는 원문과 대조하면 드러난다.
- 그런데 **"400만원"이 맞는데 농어민 조건을 빼먹으면**, 농어민인 사람은 자기가 대상인지 모른 채 지나간다. 답이 틀린 게 아니라 **불완전한데, 불완전은 조용하다.**

Stanford 연구(Magesh et al., arXiv 2405.20362)가 상용 법률 AI 3종(Lexis+ AI · Westlaw AI-Assisted Research · Ask Practical Law AI)을 실측한 결과 **환각률 17~33%**다. 벤더들이 "RAG가 환각을 제거한다"고 주장하는 것과 다르다.

→ **CUBE의 설계 목표는 "정답을 잘 맞히는 것"이 아니라 "틀릴 수 없게 만드는 것"이다.**

## 3. 발전 과정 (시간순)

### 3.0 사전 단계 — 순서 0~3 (완료)
사양 §13의 구현 순서: `numeric`(금액·해시) → `policy`(스키마·로더·거절 매트릭스) → `engine`(정렬 결정론).

### 3.1 7/31 — ★ 첫 번째 피벗: "RAG를 만들자" → "만들 수 없다"

**계기.** *"Mission 1(RAG)을 develop하고 싶다"*로 세션을 열었다.

**발견.** 착수 전 `packages/policy`를 읽다가 막혔다. 정책 팩은 `sources[].source_id`로 근거 조문을 참조하고 로더가 그 참조를 검사하는데, **검사가 하는 일은 "같은 팩 안에서 그 id가 선언돼 있는가"뿐**이었다. 팩 안에서 닫혀 있고 바깥의 실물(원문 조문)과 연결이 없었다.

→ **이건 "RAG가 아직 없다"가 아니라 "두 미션을 잇는 이음매가 비어 있다"였다.** RAG는 색인할 원문이 있어야 색인을 한다. 사양 §13의 **순서 4 "정책 코퍼스 원문 수집"이 미착수**인 채로 순서 5 이후를 건드리려던 것.

**결정.** 세션 목표를 RAG에서 순서 4로 교체.

**배운 것.** *"다음에 뭘 만들까"보다 "지금 만들려는 것이 무엇에 의존하는가"를 먼저 본다.* 순서를 건너뛰었으면 색인할 게 없었거나, 더 나쁘게는 내가 아는 세법 지식으로 빈 값을 채웠을 것이다(CLAUDE.md "하지 말 것" 2번이 정확히 금지).

### 3.2 7/31 — 수집 단위 결정: "필요한 7개"가 아니라 "그 법 전체"

법제처 API에는 `JO` 파라미터가 있어 조문 하나만 받을 수 있다. §12가 요구하는 조문은 7개니까 7번 호출하면 끝나 보였다.

**사양 §1.2를 다시 읽자 뒤집혔다.** 사양은 FACT 답변을 2클래스로 나눈다:
- `REGISTRY_RESOLVED_FACT` — Registry 룰로 승격된 확정 팩트
- `UNMODELED_OFFICIAL_SOURCE` — 미모델링이지만 **원문은 인용 가능**

→ 두 번째 클래스가 존재하는 이유는 **"모른다"와 "원문은 있으나 미모델링"을 구분하기 위해서**다. 그리고 후자는 **전 조문을 갖고 있어야만 가능하다.**

**결정.** `JO` 없이 `MST` 하나로 전 조문 일괄 수신. → 6개 법령 **1,849 조문**을 6번 호출로 확보.

**배운 것.** *lazy의 기준은 "지금 코드가 짧은가"가 아니라 "나중에 다시 안 해도 되는가"다.* 그리고 **사양의 타입 설계가 데이터 수집 전략을 결정했다.**

### 3.3 7/31 — ★ 버그 3개: 전부 "에러를 내지 않는" 종류

| # | 버그 | 어떻게 잡혔나 | 결과 |
|---|---|---|---|
| 1 | 편·장·절 표제("전문")가 **뒤 조문의 번호를 달고 와서** `source_id` 충돌 | 6건 중 5건 실패 | `조문여부` 명시 필드로 전환 → 6/6 |
| 2 | 응답 JSON **key 순서**에 의존해 조문 첫 문장이 맨 뒤로 밀림 | 눈으로 발견 | 명시적 조립(조문내용→항→호→목) |
| 3 | `목내용`이 **배열의 배열**로 와서 세목 유실 | **증상 없음** — 자체 검산이 throw | **6만 5천 자 복구** (1,852,000 → 1,917,666자) |

**★ 버그 1의 진짜 교훈.** 첫판에 유일하게 "성공"한 `RETIRE_D`도 충돌만 안 났을 뿐 같은 오염 위험이었다. **충돌 시 "그냥 덮어쓰기"로 짰다면 6개 전부 조용히 성공했고, 오염된 코퍼스 위에 정책 팩을 쌓았을 것이다.** → *"실패 5건"이라는 나쁜 결과가 사실은 방어 장치가 일한 증거였다.*

**★ 버그 3의 교훈.** 증상이 없는 버그는 검산 장치가 없으면 영원히 안 보인다. 그리고 곁가지 — *검산 장치가 처음 잡는 건 대개 검산 장치 자신의 버그다.* 여기서 "검산이 시끄러우니 끄자"로 가면 진짜 버그를 영원히 못 만난다.

### 3.4 7/31 — ★ 측정 후 기각한 heuristic (발표 핵심)

법제처 API가 `목`을 `호`의 자식이 아니라 **`항`의 형제**로 내려준다. 부모 호 참조가 없다. 그냥 순서대로 이어붙이면:

```
1. 다음 각 목의 어느 하나에 해당하는 경우: 400만원   ← 가·나·다는 여기 소속
2. 제1호에 해당하지 아니하는 자의 경우: 200만원
가. 직전 과세기간의 총급여액이 5천만원 이하인 거주자…  ← 2번 뒤에 붙음
```

**읽으면 "총급여 5천만원 이하 → 200만원"으로 뒤집힌다.** 실제로는 400만원(서민형)이다. 사양 §12가 1순위로 지정한 파라미터가 정반대가 되는 상황.

**heuristic 후보:** 법률 작성 관행상 "다음 각 목"이라 말하는 호만 목을 가진다 → 그런 호에 목 묶음을 순서대로 매칭.

**채택 전에 측정했다.** 4개 법령 **238개 항 실측 → 80.3% 일치(191/238), 47건 불일치.**

**→ 기각.** 이 도메인에서 80.3%는 "꽤 맞음"이 아니라 **"5건 중 1건을 조용히 틀리게 붙인다"**이다. 대신 소속 미상 목에 **`[각 목]` 표식**만 달아 "어느 호 소속인지 모른다"를 텍스트에 드러낸다.

**배운 것.** ***틀린 구조를 주장하느니 모른다고 하는 편이 낫다.*** 그리고 그 판단을 **감이 아니라 238개 항 실측으로** 내렸다는 게 핵심이다.

### 3.6 7/31 — ★ 설계 정정: 사양을 과하게 좁게 읽었다

이전 계획은 "승인된 규칙이 없으면 원문만 던지고 끝"이었다. 다시 읽으니 §7이 금지하는 것은 "AI가 값을 **결정**한다"이고, §1.2 UNMODELED 행은 **"개인 상황 적용 금지 · PLAN 엔진 입력 금지"**라고만 한다 — **숫자 언급을 금지하지 않는다.**

| | 예시 | 판정 |
|---|---|---|
| 인용·종합 | "조문에 따르면 400/200만원, 조건은 …[원문]" | ✅ |
| 개인 적용 | "**당신은** 400만원입니다" | ❌ §1.2 |
| 계산 투입 | 400만원을 Tax Calculator 입력으로 | ❌ 절대 규칙 1·3 |

그리고 400↔200 사고는 **LLM이 못 읽어서가 아니라 파싱이 원문을 망가뜨려서**였다. 교훈은 "LLM에게 읽히지 마라"가 아니라 **"원문을 온전하게 줘라"**였다.

### 3.7 7/31 밤 — Router: 부탁하지 말고 배선으로 막아라

**문제.** "나 연봉 6천인데 IRP 얼마 넣어야 돼?"를 FACT 엔진에 넣으면 LLM이 개인 맞춤 답을 쓰려 한다. 프롬프트에 "그러지 마"라고 적는 건 사후 방어다.

**결정 — LLM 없이 규칙 기반.** 이유 셋:
1. **재현성(§1.3)** — 같은 질문은 항상 같은 분기. LLM 분류기는 그 보장이 없다.
2. **비용** — 라우팅에 콜을 쓰면 걷어낼 질문에 돈을 쓴다.
3. **손해가 비대칭** — PLAN→FACT로 새면 §1.2가 뚫린다. 반대는 안내 후 다시 물으면 된다. → **PLAN 쪽으로 기울였다.**

**두 번 틀렸고 둘 다 테스트가 잡았다:**
- **한국어 부분문자열** — `내`·`제`·`저`를 `includes`로 잡으니 **제55조·국내·저축·내국법인**이 전부 PLAN으로. → 조사까지 붙은 토큰(`내가`·`제가`)만.
- **나이 수치** — `40세 이상 가입 제한이 있나`가 PLAN으로 갔다. 원인이 흥미롭다: **나이는 조문에도 흔히 나오는 수치**고, **연봉·월급 액수는 조문이 절대 쓰지 않는 표현**이다. → 나이는 "약한 신호", 연봉은 "강한 신호".

**검증:** 고정 케이스 22건. **PLAN 질의는 검색·LLM을 아예 안 탄다(API 콜 0회)** 실측 확인.

### 3.8 7/31 밤 — UI: 계산 금지를 리뷰가 아니라 grep으로

`packages/factui`는 `node:http` + 정적 파일. **React/Vite 없음, 새 의존성 0.** 브라우저 JS는 fetch + `innerHTML`이 전부(**35줄**).

부수 효과 둘: ① 계산 금지 grep이 파일 몇 개만 훑으면 되고 ② 합성 스탬프가 DOM에 실제로 있는지 **브라우저 없이 문자열로 확인**된다.

**검사기를 만들며 배운 것 — 오탐과 미탐은 같이 봐야 한다.** 오탐 2건(`127.0.0.1`의 `0.0`이 세율로, 예시 칩 `"IRP 납입한도"`가 하드코딩 값으로)이 나왔다. 좁히기만 했으면 검사가 약해졌을 것이다. 좁히는 김에 "그럼 이건 잡히나?"를 물어 2건을 더 찾았다(`const nonTaxLimit = 20000000;`, `base * 12`). 그리고 **탐지기 자신을 검증하는 테스트**(미끼 `income * 0.15`)를 넣었다.

### 3.9 8/3 — 측정 세션들

- **스트리밍** — 막고 있던 것은 기술이 아니라 **번호를 매기는 순서**였다.
- **비교는 표로** — "빈 칸은 모른다는 사실을 지운다".
- **★ 재보니 내 설명 두 개가 틀렸다** — 측정 세션에서 스스로의 주장 2건이 실측과 달랐다.
- **★ 유형별 평가셋을 만들자 점수가 무너졌다** — 그동안 쉬운 시험을 치고 있었다.
- **★ 자동 검사를 다 통과한 답이 숫자를 지어냈다** → 기계 교차검증(`check:cross`) 신설. **검사자 `gemini-2.5-flash` / 작성자 `claude-sonnet-5` — 서로 다른 provider(사양 §2.2 독립성).** 21문항 중 ○16 · ✗5.
- **지어낸 금액 검사기(`amounts.ts`)** 신설.

### 3.10 8/4 — ★ 사용자 질문 하나가 안전 구멍을 열었다 (발표 핵심)

**계기.** 사용자: *"대강 내 상황 적은 다음에 '이런 경우에 이건 얼마야?' 하면 답 나와?"*

**"안 됩니다"라고 답하는 대신 실제로 던져봤다.**

| 질문 | 결과 |
|---|---|
| `"나는 총급여 5천만원 직장인이고… 세액공제 얼마 받아?"` | ✅ PLAN 차단 · API 0콜 |
| `"총급여 5천만원인데 연금저축 600만원 넣으면 세액공제 얼마 받아?"` | ❌ **FACT로 샜다** |

새어나간 답: *"세액공제 받는 금액은 **90만원**이다. 계산식은 600만원 × 15%다[1]."*

**위반 셋이 겹쳤다:** ① §1.2 개인 적용 금지 ② **절대 규칙 3 — 계산 경로 LLM 금지** ③ Router 누락.

**다만 세 번째 그물은 작동했다** — 전날 만든 금액 검사기가 `미확인 금액 2건`을 띄웠다. `90만원`은 어느 조문에도 없다. *막지는 못했지만 조용히 지나가지도 않았다.*

**배운 것.** ① **"됩니까?"에 말로 답하지 말고 던져봐라.** ② **그물이 셋이어서 살았다.** ③ **막는 규칙을 넓히면 정상 질의가 막힌다** — 실제로 소득 패턴을 넓혔다가 `"총급여 5천만원 이하면 공제율이 몇 %인가"`(명백한 FACT)를 걷어내는 오탐을 만들었다가 잡았다.

### 3.11 8/4 — 미션 2 최소판 (`@cube/plan`)

사용자: *"부족하면 뭐가 부족하다 알려주고."* — 마지막 문장이 설계를 다 정했다.

- **값은 승인된 규칙에서만** (`registry.resolveEffect`, 하드코딩 0)
- **계산은 코드가** (LLM은 이 경로에 안 들어옴)
- **모자라면 무엇이 모자란지** — `NEEDS_INPUT` / `NEEDS_RULE`
- **입력 추출도 LLM을 안 쓴다** — 잘못 읽으면 그 뒤 계산이 전부 틀리는데 계산 자체는 정확해서 검증기가 못 잡는다

**되묻기 — 보기(선택지)는 승인된 규칙에서만 나온다.** 규칙이 없으면 보기 없이 직접 입력만 받고 *"이 항목의 기준값이 아직 승인되지 않아서입니다"*라고 말한다. → **보기가 없다는 것 자체가 정보다.**

### 3.12 8/7 — ★ 두 번째 피벗: 레포 분리

미션 2(절세 계획 로직)를 `../A4-Logic/`으로 분리. 각각 완성 후 합친다.

- **나간 것:** `taxlens`(τ·격자·구간표·시뮬·역산·성향) · `engine`(MechanismInstance·정렬키)
- **남은 것:** `corpus` · `factindex` · `fact` · `factui` · `packdraft` · `plan`
- **`numeric`·`policy`는 양쪽에 같은 사본. ❄ 수정 금지** — 한쪽만 고치면 조용히 갈라진다.
- **`policy/packs/`의 주인은 A4-RAG다.** 초안 생성과 사람 승인이 여기서 일어나고, A4-Logic은 승인된 팩을 읽기 전용 사본으로 받는다.

## 6. 내가 직접 한 주요 의사결정

발표에서 "왜 그렇게 했나"를 물었을 때 답할 수 있는 것들.

| 결정 | 대안 | 왜 이걸 골랐나 |
|---|---|---|
| **순서 4(코퍼스)를 먼저** | 바로 RAG 착수 | 색인할 원문이 없었다. 순서는 관료 절차가 아니라 **의존성 그래프** |
| **전 조문 일괄 수집** | 필요한 7개만 | 사양 §1.2의 FACT 2클래스가 데이터 전략을 결정. §12 밖 질문에 "원문은 있으나 미모델링"으로 답하려면 전 조문 필요 |
| **목 소속 heuristic 기각** | 80.3% 채택 | 이 도메인에서 20% 오류 = "5건 중 1건을 **조용히** 틀리게 붙임" |
| **Router를 LLM 없이** | LLM 분류기 | 재현성(§1.3) + 비용 + **손해의 비대칭**(PLAN→FACT로 새면 §1.2가 뚫림) |
| **React 안 씀** | Vite + React | 안 쓰면 `app.js`가 35줄이고, **계산 금지를 grep으로 증명**할 수 있다 |
| **시행예정 = ENACTED** | PROPOSED | 이미 공포된 법이고 시행일만 미래. PROPOSED로 뒀으면 순서 2 R61에 걸려 **영원히 계산에 못 들어감** |
| **반올림 필드를 아예 뺌** | enum 완화 / placeholder 허용 | 거절 매트릭스 R15가 이미 답을 갖고 있었다 — "일부만 있으면 거절"이니 **전부 없는 것은 유효** |
| **막는 쪽 대신 주는 쪽을 넓힘** | Router 마커 확장 | 앞서 확장했다가 정상 FACT 질의를 걷어낸 오탐을 만들어봤기 때문 |
| **effort=medium 채택** | high 유지 / low | 넓은 질문 28% 단축, 품질 차이 노이즈 안 (§7.3) |
| **질의 분해 안 만듦** | 논문 권고대로 구현 | 진단해보니 **검색은 성공**했고 낮은 점수는 채점기가 만든 것이었다 (§7.5) |

| 3 | **묶음**에 bare 참조 확장 | 실재율 80.4% (dangling 788건은 대부분 「삭제」 스텁) | ✅ **채택** |
| 4 | LLM rerank | 순증 +2, **1건 망침** | 🟡 보류 (표본 26건) |
| 5 | 프롬프트 캐싱 | 27,781토큰 캐시 히트에도 **0.35초(3%)** | ❌ 안 씀 |
| 6 | scope 결정론 분류기 | A/B에서 패배 (앵커 68.8% vs 87.5%) | ❌ 삭제 |
| 7 | AI-2 double check | 47.7초로 **2배 느려지고 품질도 저하** | ❌ 폐기 |
| 8 | Haiku 선별 → Sonnet 작성 | 전제가 실패 | ❌ 폐기 |
| 9 | 섹션 병렬 생성 | 처리량 2.8배지만 **출력 2.2배** | ❌ 폐기 |

**★ #2와 #3이 같은 16%인데 판정이 갈린 이유 (발표용):**

| | 인용 그래프 (기각) | 묶음 확장 (채택) |
|---|---|---|
| 무엇인가 | "이 조문이 저 조문을 인용한다"는 **사실 주장** | 조문을 **후보로 넣는 것** |
| 틀리면 | 근거가 거짓이 된다 | 질문과 무관해 LLM이 인용 안 함 → 버려짐 |
| 비용 | 정확도 | **프롬프트 토큰** |

→ ***용도가 다르면 기준도 다르다.***

### 7.2 ★ 8/7 — thinking 실험 4칸: 가설이 전부 틀렸다

넓은 질문 답변이 30초 걸리는 게 문제였다. 원인을 "생각(thinking)을 너무 많이 한다"로 가정하고 4칸을 측정했다. **전부 baseline보다 느렸다.**

| 설정 | 좁은질문 시간 | 판정 |
|---|---|---|
| high + adaptive (기준) | 8.5초 | — |
| high + 생각 억제 프롬프트 | **13.2초** | ❌ 재생성 3/10 발생 |
| high + thinking 완전 차단 | **10.9초** | ❌ 답이 오히려 길어짐 |
| medium + 생각 억제 | 9.3초 | ❌ |
| medium + thinking 차단 | 9.3초 | ❌ |

**→ 병목은 thinking이 아니었다.** 좁은 질문에서 시간을 먹던 건 그냥 **답변 텍스트를 쓰는 시간**(523자 ≈ 8.4초, 약 66자/초)이었고, adaptive thinking은 애초에 거의 안 돌고 있었다. 생각을 줄이라고 하면 답이 오히려 길어지고 계산 금지 규칙을 더 자주 어겨 재생성이 붙었다.

### 7.3 ★ 8/7 — 진짜 레버는 `effort`였다

**발견.** 코드가 Anthropic API에 `model` · `max_tokens` · `system` · `messages` 네 개만 보내고 있었다. **`effort`도 `thinking`도 안 보냈다.** Sonnet 5의 API 기본값은 `effort=high` + adaptive thinking. 즉 하루 종일 "가장 깊게 생각하는" 설정으로 돌면서 아키텍처로 속도를 줄이려 하고 있었다.

**7칸 스윕 후 `medium` 채택. ×3 반복 측정:**

| | 앵커 | 시간 | 길이 |
|---|---|---|---|
| 넓은질문 high (기준) | 87% | **30.9초** | 1,320자 |
| **넓은질문 medium** | **85%** | **22.2초** (×3: 22.2/21.8/22.5) | 1,317자 |
| 좁은질문 high | 82~89% | 8.85초 | 564자 |
| 좁은질문 medium | 85~89% | 8.4초 | 523자 |

**★ 넓은 질문은 답 길이가 똑같은데(1,317 vs 1,320자) 시간만 28% 줄었다.** 같은 분량을 쓰면서 9초가 사라졌으면 그건 텍스트가 아니라 thinking이다. 즉 **좁은 질문은 텍스트가 전부고, 넓은 질문은 thinking이 3분의 1**이었다.

**품질 손실 0** — 인용률 100%, 위조 인용 0건 동일. 앵커 2%p 차이는 노이즈 범위.

**추가 시도도 재보고 버렸다:**
- `effort=low` → 17.7초(-20%)지만 가장 복잡한 문항 앵커가 **100% → 40%**. 평균만 보면 안 보이는 패턴이라 폐기.
- 간결 지시 프롬프트 → 길이 5% 감소, 시간 0.5초. **사실상 무효.** Sonnet 5는 답 길이를 과제 복잡도에 맞춰 스스로 정하고 프롬프트로 안 밀린다.

### 7.4 ★ 8/7 — 채점기 자체가 틀렸다는 발견

**계기.** 넓은 질문 Q8이 4회 중 한 번만 앵커 25%였다(나머지 60~67%). 답을 직접 읽어보니 **잘 쓴 답**이었다.

**원인.** 채점기가 지적한 "누락"이 오탐이었다:
- 원문은 `100분의5`, 답변은 `5%` → **문자열 매칭 실패**. 연령별 세율표가 버젓이 있는데 셋 다 누락으로 셈.
- 소득세법 제129조(원천징수세율, 호 17개)를 인용하면 **이자·배당 원천징수율까지 전부 열거하라고 요구**.

**→ 조문을 하나 더 정확히 인용하고 정보를 더 준 답이 점수가 반토막 났다.** Q1도 같은 패턴(조문 3건 인용한 회차만 100%→80%).

**문헌 확인.** Attribution 서베이(arXiv 2508.15396)는 기존 지표들이 **큰 문서를 인용했다고 그 내용을 전부 재현하라고 요구하지 않는다**고 명시한다. ALCE의 citation recall은 분모가 **답변의 문장**인데, 우리 앵커는 분모가 **조문의 수치 전부**였다 — 방향이 정반대였다.

**수정.** `100분의N` ↔ `N%` 정규화 + 숫자 경계 검사(`5%`가 `15%`에 안 걸리게).

**재채점 (API 0회 — 저장된 답변을 그대로 다시 채점):**

| | 수정 전 → 후 |
|---|---|
| 좁은질문 high | 78→82 · 82→89 |
| 좁은질문 medium | 84→89 · 80→85 · 83→87 |
| 넓은질문 high | 76→**87** |
| 넓은질문 medium | 73→**85** |
| user 세트 | 58→74 · 61→70 |

**81문항 중 80개 상승, 1개 하락.** 하락한 1건은 짧은 비율 토큰이 다른 수치에 붙어 점수를 부풀리던 걸 경계 검사가 잡은 것 — 조이는 쪽도 실제로 작동한다는 증거.

**→ 우리 품질이 측정치보다 좋았다.** 넓은 질문 앵커가 73~76%인 줄 알고 "부족하다"고 판단해왔는데 실제로는 83~90%였다.

### 7.5 ★ 8/7 — 만들려다 만들지 않은 것: 질의 분해

`ISA·연금저축·IRP 3자 비교` 문항이 모든 설정에서 앵커 31~45%로 최하위였다. 연구 문헌은 multi-hop 질문에 **질의 분해**(서브질의로 쪼개 각각 검색 → 병합 → 리랭크)를 권한다.

**만들기 전에 진단했다.** 리포트를 열어보니:
- **기대 조문 2개가 이미 다 인용돼 있었다** → 검색은 성공
- 답변에 12%·15%·5,500만원·4,500만원이 들어간 제대로 된 비교표였다
- 낮은 점수는 §7.4의 채점기 결함이 만든 것 (재채점 후 **57%**)

**→ 분해는 틀린 처방.** 연구가 말한 "한 번의 검색으로 근거 사슬을 못 가져온다"는 전제가 우리 케이스엔 성립하지 않았다. 만들었으면 검색 구조를 크게 바꿔놓고 아무것도 못 고쳤을 것이다.

### 7.6 ★ 8/7 — 시도했다가 되돌린 것: 과반 게이트

§7.4 수정 후에도 큰 조문(제129조)의 무관한 세율이 누락으로 잡혔다. 게이트를 `hit >= 2`에서 `hit > missing`(과반)으로 조여봤다.

**30분 전에 짜둔 회귀 테스트가 잡았다.** 답변이 **나이(70세·80세)는 맞고 세율은 셋 다 틀린** 경우, 과반 게이트는 그 호를 "안 다뤘다"고 건너뛰어 **100점을 준다.** "큰 호를 스쳤다"와 "다뤘는데 숫자를 틀렸다"를 구분 못 한다. 전 리포트 평균이 84~98%로 뛴 것도 지표가 측정을 멈췄다는 신호였다.

**→ 되돌리고 `KNOWN-LIMITATION` 마커에 이유·재현법·업그레이드 경로를 남겼다.**

## 8. 기존 방식 대비 차별점

| | 일반적인 법률 RAG 챗봇 | CUBE (A4-RAG) |
|---|---|---|
| 출처 | 있다고 말하지만 **지어낼 수 있음** (상용 도구 환각률 17~33%) | **닫힌 집합** — 제공 조문 밖 `[n]`은 기계적으로 위조 판정 |
| 원문 | 요약해서 넣음 | **전문 그대로.** 요약하면 조건이 날아간다 |
| 모르는 것 | 그럴듯하게 채움 | `[각 목]` 표식 · "확인되지 않는다" · `NEEDS_RULE` |
| 개인 맞춤 | 프롬프트로 "하지 마"라고 부탁 | **Router가 배선으로 차단** (API 콜 0회) |
| 계산 | LLM이 함 | **코드가 함.** LLM은 계산 경로에 안 들어옴 |
| 세법 값 | 코드에 하드코딩 | **정책 팩(사람 승인)에서만.** 하드코딩은 grep 테스트가 차단 |
| 재현성 | 없음 | 조문 SHA-256 · `ragIndexVersion` · 프롬프트 버전 · **모델+effort까지** 매니페스트에 기록 |
| 시점 | 무시 | 조문 `validFrom` + **본문의 적용기한 스캔**(`validFrom`이 못 잡는 것) |

**핵심 가치 한 줄:** *다른 시스템은 "맞히려고" 하고, CUBE는 **"틀릴 수 없게"** 만든다.*

## 10. 발표에서 강조할 것

### 10.1 핵심 스토리 (3분 버전)

> **"세법 챗봇에서 제일 위험한 건 틀린 답이 아니라 조용히 불완전한 답이다."**
>
> ISA 비과세 한도를 물으면 "400만원"이라고 답할 수 있다. 맞는 답이다. 그런데 그게 **총급여 5천만원 이하일 때만** 400만원이고 나머지는 200만원이라는 조건을 빼먹으면, 해당자는 자기가 대상인지 모른 채 지나간다. **틀린 게 아니라 불완전한데, 불완전은 아무 소리도 내지 않는다.**
>
> 그래서 CUBE는 "맞히는" 시스템이 아니라 **"틀릴 수 없게 만드는"** 시스템으로 설계했다.
> 인용은 닫힌 집합이라 지어낼 수 없고, 원문은 요약 없이 통째로 주고, 모르는 건 `[각 목]` 표식으로 모른다고 쓰고, 개인 맞춤 질문은 LLM에 **도달하기 전에** 배선으로 차단한다.
>
> 그 과정에서 **80.3%짜리 좋아 보이는 방법을 재보고 버렸고**, 검산 장치가 **6만 5천 자의 조용한 유실**을 잡았고, 오늘은 **채점기 자체가 틀렸다는 것**을 발견했다.

### 10.2 숫자로 말할 수 있는 것

```
코퍼스        법령·행정규칙 10종 · 2,137 조문 · SHA-256 고정
검색          hit@1 22/26 (85%) · hit@5 25/26 · 벡터 DB 없이 메모리 코사인
답변          위조 인용 0건 (전 실행) · 기대 조문 인용률 100% (전 실행)
              조건 앵커 좁은 87% · 넓은 85%
속도          넓은 질문 30.9초 → 22.2초 (28% 단축, 품질 손실 0)
              좁은 질문 8.4초 · 스트리밍 첫 글자 0.3초
테스트        508 통과 / 0 실패 · 새 의존성 0
비교          상용 법률 AI 환각률 17~33% (Stanford 실측)
```

> ⚠️ **정직하게 붙일 단서:** 상용 도구의 17~33%는 "법적 주장이 틀렸는가"를 재고, 우리 위조 인용 0건은 "인용 번호가 제공 범위 밖인가"를 잰다. **우리 검사가 훨씬 좁다.** 나란히 놓으면 과장이다. 다만 "닫힌 집합 인용 + 검증 게이트"라는 **설계 선택이 왜 필요한지**를 보여주는 근거로는 유효하다.

### 10.3 예상 질문 → 한 줄 답

| 질문 | 답 |
|---|---|
| "RAG 만든다더니 왜 데이터 수집을?" | 정책 팩이 참조하는 `source_id`의 실물이 레포에 없었습니다. 색인할 원문 자체가 없었어요 |
| "필요한 조문 7개만 받으면 되지 않나요?" | 사양이 FACT를 2클래스로 나눕니다. "모른다" 대신 "원문은 있으나 미모델링"으로 답하려면 전 조문이 필요합니다 |
| "80%면 꽤 정확한데 왜 안 썼나요?" | 이 도메인에서 80.3%는 "5건 중 1건을 **조용히** 틀리게 붙인다"입니다. 하필 그 사례가 ISA 400/200만원 뒤집힘이었습니다 |
| "AI가 세법 값을 뽑는데 어떻게 믿죠?" | **안 믿습니다.** AI-1 초안 → AI-2(다른 provider) 반박 → 원문 대조 → **사람이 YAML을 손으로 편집.** 승인 버튼이 없는 이유는 버튼이 있으면 원문을 안 보기 때문입니다 |
| "개인 맞춤 답변은 왜 안 되나요?" | 사양이 미모델링 답변의 개인 적용을 금지합니다. **프롬프트로 부탁하는 대신 Router가 그 질문을 LLM에 도달 못 하게** 합니다 — API 콜 0회 |
| "UI가 계산 안 한다는 걸 어떻게 보장하죠?" | 소스를 grep하는 테스트가 있고, **그 검사기가 진짜 잡는지도 미끼를 심어 테스트**합니다 |
| "지금 답이 전부 '팩트 결론 아님'이던데요?" | 맞습니다. 승인 규칙이 아직 적어 대부분 `UNMODELED_OFFICIAL_SOURCE`입니다. **숨기지 않고 라벨과 매니페스트에 그대로 씁니다** |
| "속도는 더 못 줄이나요?" | 남은 22초는 **1,300자를 쓰는 시간**입니다. 더 줄이려면 답에서 뭘 빼야 하는데, 두 실험이 뺄 게 없다고 말했습니다. 대신 스트리밍으로 첫 글자가 0.3초에 나옵니다 |
| "품질은 검증됐나요?" | **아직입니다.** 기계가 잰 건 형식이고, "그 문장이 사실인가"는 사람이 봐야 합니다. 리포트의 `사람 검증:` 칸이 비어 있고, 기계 교차검증 `✗` 5건이 먼저 볼 목록입니다 |

### 10.4 배운 것 (기술 외)

1. **측정하지 않은 개선은 개선이 아니다.** 80.3%도, rerank +2도, effort medium도 전부 재고 나서 판단했다. 오늘만 해도 ×1 결과로 "medium이 빠르다"고 했다가 ×3으로 재보니 **좁은 질문은 차이가 없었다.**
2. **검사 장치가 결과에 맞춰 무뎌지면 안 된다.** 과반 게이트를 넣었더니 전 리포트가 96%로 뛰었는데, 그건 지표가 측정을 멈췄다는 뜻이었다. **회귀 테스트가 그걸 잡아줬다.**
3. **측정기부터 의심하라.** curl이 한글을 깨뜨려 "① 0건"으로 오판한 적이 있고, 오늘은 **채점기 자체가 틀렸다.** 리포트 파서도 답변의 `##` 제목에서 쪼개져 10문항을 5문항으로 읽고 있었다.
4. **"할 수 있는데 안 한 것"과 "못 한 것"을 구분해서 말한다.** 파라미터 추출은 전자(승인 절차가 필요)고, 목 소속 호는 후자(API 한계)다. 뭉뚱그리면 어느 쪽도 신뢰를 못 얻는다.
5. **그물은 여러 겹이어야 한다.** 8/4 사고에서 Router 실패 → 프롬프트 실패 → **금액 검사기가 작동**했다. 하나만 있었으면 조용히 틀렸다.

## 11. 부록 — 재현 명령

### 데모 · 회귀

```bash
start.bat                                    # 데모 서버 → 127.0.0.1:8787
                                             # (또는 npm run serve -w @cube/factui)
npm test                                     # 전체 회귀 508 테스트
npm run check:retrieval -w @cube/factindex   # 검색 정확도 게이트 (hit@1 22/26)
npm run check:bundle -w @cube/fact           # 묶음 적중률
npm run ask -w @cube/factindex -- "질문"      # 검색만 (답변 생성 없음)
npm run answer -w @cube/fact -- "질문"        # CLI 답변
```

### ★ 발표에서 인용한 실험 재현

> **여기가 이 프로젝트의 주장을 뒷받침한다.** 인용한 숫자는 전부 다시 돌릴 수 있다.

```bash
# 80.3% — 목 소속 heuristic 을 기각시킨 측정 (§3.4)   ※ API 0콜
npm run measure:mok -w @cube/corpus

# 16% / 80.4% — bare 참조 확장 판단 (§7.1 #2·#3)     ※ API 0콜
npm run measure:bareref -w @cube/factindex

# rerank ablation — 순증 +2, ★망침 1 (§3.5 Phase 7)
npm run ablate:rerank -w @cube/factindex

# 적용기한 스캔 — validFrom 이 못 잡는 것 (§8 '시점') ※ API 0콜
npm run scan:deadlines -w @cube/corpus

# 저장된 답변을 새 채점기로 다시 채점 (§7.4)          ※ API 0콜
npm run rescore -w @cube/fact
```

### 답변 품질 측정 (API 사용 — 비용 발생)

```bash
npm run check:answers -w @cube/fact -- --set wide
npm run check:answers -w @cube/fact -- --set narrow --effort medium --thinking adaptive --run 2
npm run check:answers -w @cube/fact -- --set narrow --limit 0    # 설정만 확인 (API 0콜)
npm run check:cross -w @cube/fact                                # 기계 교차검증 (다른 provider)
```

### 정책 팩 승인 파이프라인 (사양 §2.2 Maker-Checker)

```bash
npm run draft   -w @cube/packdraft   # AI-1: 조문 → 규칙 초안
npm run review  -w @cube/packdraft   # AI-2(다른 provider): 초안 반박 + 원문 대조표
npm run promote -w @cube/packdraft   # 사람이 손으로 편집한 YAML 을 승격
npm run check:approved -w @cube/plan # 승인된 규칙으로 계산되는지 확인
```
